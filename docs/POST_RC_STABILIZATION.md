# Sprite Station Studio v0.9.0 — Post-RC Stabilization

Текущая ветка: `post-rc/0.9.0-stabilization`.

Опубликованный prerelease: tag `v0.9.0-rc1`, artifact commit `df8613c5d44be876672273692c32520e0631b59d`.

## Цель

Стабилизировать v0.9.0 Static Sprite Workflow после публикации RC1, не расширяя release scope и не изменяя проверенные публичные контракты без доказанного дефекта.

## Разрешено

- исправлять воспроизводимые дефекты RC1;
- добавлять regression-тест до или вместе с исправлением;
- усиливать безопасные валидаторы, no-overwrite, rollback и read-only audit;
- улучшать воспроизводимость сборки и проверки release artifacts;
- уточнять документацию на основе фактически пройденных проверок.

## Не входит в post-RC scope

- возобновление AI Center;
- новые платные API-вызовы;
- новые форматы manifest без отдельной миграции;
- массовый рефакторинг `gui.py`;
- новая архитектура Job System для всех модулей одновременно;
- AtlasBuilder, Godot, Unreal, installer или updater как новые функции;
- объявление Stable без отдельного решения.

## Обязательный цикл дефекта

1. Зафиксировать воспроизводимый сценарий и затронутый контракт.
2. Добавить failing regression test либо объяснить, почему real smoke является единственным доказательством.
3. Выполнить минимальное исправление.
4. Запустить целевые тесты и полную Python regression.
5. Для Blender/Unity изменений выполнить соответствующий real smoke.
6. Проверить rename boundaries: активный бренд Sprite Station Studio, legacy только по allowlist.
7. Зафиксировать отдельный коммит и синхронизировать post-RC ветку.

## Когда нужен RC2

RC2 создаётся только если post-RC исправление меняет файлы пользовательского приложения, публичный контракт, Blender/Unity worker или содержимое распространяемого ZIP. Изменения только тестов, документации и внешних release-verification tools не требуют немедленного RC2.

Перед RC2 обязательны новый commit-bound ZIP, новый SHA-256 manifest, clean extraction, полный regression, synthetic E2E и затронутые physical smoke tests.

## Stable gate

Stable требует отдельного решения после периода проверки prerelease. Минимальные условия: отсутствие открытых блокирующих дефектов, повторяемая установка/запуск, подтверждённый artifact hash, документация ограничений и решение по поддерживаемой Windows-конфигурации.
